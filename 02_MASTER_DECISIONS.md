# TruckMate — Master Decisions

Only explicit project decisions belong here. Preserve superseded decisions rather than silently rewriting history.

| ID | Status | Decision | Rationale |
|---|---|---|---|
| TM-D001 | SUPERSEDED | Product name is **TruckMate** as the working/project name; public branding is not cleared until naming-conflict review is complete. | Superseded by TM-D056 after the owner selected CabPilot as the public brand. |
| TM-D002 | ACTIVE | PWT structure is adaptive; no fixed SRS section count. | Structure follows actual project complexity. |
| TM-D003 | ACTIVE | Current Load Card is the center of the driver's working-day experience. | Highest-frequency information should be immediately available. |
| TM-D004 | ACTIVE | Product principle: clean, easy, simple; collect once and reuse everywhere. | Reduce repetitive driver work. |
| TM-D005 | ACTIVE | User tiers are based on functional needs, not job title. | Percentage-paid drivers may need the same financial layer as owner-operators. |
| TM-D006 | ACTIVE | TruckMate is not an ELD replacement. | Keep V1 focused and avoid unnecessary compliance/technical scope. |
| TM-D007 | ACTIVE | Driver operational/business data is private by default and shared only by user action. | Trust and privacy are core product requirements. |
| TM-D008 | ACTIVE | Deadhead tracking is configurable/optional. | Carrier compensation practices differ. |
| TM-D009 | ACTIVE | Load documents remain grouped with the load: confirmation/rate con, pickup BOL, signed delivery/POD, plus flexible Other Load Documents. | Eliminates searching across photos/email while accommodating real paperwork without category bloat. |
| TM-D010 | ACTIVE | Use an existing/native scanning component rather than building scanner technology. | Faster, safer V1. |
| TM-D011 | ACTIVE | Gemini is the current AI direction for document classification/extraction. | Project owner's chosen AI stack. |
| TM-D012 | ACTIVE | Gmail automation is deferred; V1 can import/upload/share/scan documents. | Avoid making Gmail verification/integration a launch dependency. |
| TM-D013 | ACTIVE | Subscriptions/payment gates come after real-life product testing. | Prove utility before monetization friction. |
| TM-D014 | ACTIVE | Trial should expose the real product rather than an artificially crippled version. | User should experience actual value before subscribing. |
| TM-D015 | ACTIVE | Check-in/out events can generate reusable copy/share status messages. | Collect once, use everywhere. |
| TM-D016 | ACTIVE | Where confidence is sufficient, normal document actions may advance load stage (e.g. pickup BOL can imply pickup completion); ambiguous cases require confirmation. | Reduce redundant taps without silently corrupting trip state. |
| TM-D017 | ACTIVE | V1 supports multiple pickups and/or deliveries on a load. | Multi-stop freight is a normal real-world workflow and should not require later structural redesign. |
| TM-D018 | ACTIVE | A driver may have one Current Load plus one or more Upcoming/Pre-planned Loads. Every document/action must be attributable to the correct load; the app must not silently attach ambiguous scans. | Drivers are commonly pre-planned before the current load is complete; explicit attribution prevents state/data corruption. UI label is **Next Loads** (TM-D057). |
| TM-D019 | ACTIVE | Check-in/out records preserve timestamp provenance: system-captured versus manually entered/edited. Manual correction remains allowed. | Detention records should show how the time was obtained without preventing legitimate corrections. |
| TM-D020 | ACTIVE | Load History and search are V1 base functionality for all users, not Pro-only analytics. | Drivers need fast retrieval of past loads and paperwork; this directly implements collect-once/reuse-everywhere. |
| TM-D021 | ACTIVE | Driver interaction while the vehicle is moving must be minimized; core workflows shall not depend on multi-field forms or required typing while driving. | Reduce distraction and keep the product aligned with safe in-cab use. Clarified by TM-D059: design principle only; no in-motion restriction in V1. |
| TM-D022 | ACTIVE | Architecture should allow future team-driver/shared-load access without making it V1 scope. | Avoid a single-owner schema dead end while keeping V1 simple. |
| TM-D023 | ACTIVE | Gemini/document-processing endpoints require usage/cost-abuse controls such as server-side limits/quotas before production. | Prevent runaway API cost and abuse without changing the user-facing V1 workflow. |
| TM-D024 | ACTIVE | V1 is offline-first wherever technically possible: cached Current/Upcoming Load data, documents already downloaded, edits, check-in/out, PTI, expenses, and other local actions remain usable offline and sync later. Internet-dependent fetches, cloud AI, live routing/traffic, and fresh facility/public data wait for connectivity. | Drivers routinely work in poor/no-signal areas. |
| TM-D025 | ACTIVE | Offline check-in/out is V1 core. Save local timestamp plus device location when permission/location is available; preserve capture provenance and sync state; sync idempotently when connectivity returns. | Keep detention/work records usable without signal while avoiding duplicate events. |
| TM-D026 | ACTIVE | Essentials wallet provides standard document slots plus user-created custom document types. Custom documents receive the same expiration-date/reminder behavior when applicable. | Preserve simplicity without restricting real driver paperwork. |
| TM-D027 | ACTIVE | V1 includes both Quick PTI and Detailed PTI. Both are timestamped and saved to inspection history; notes/photos may document issues. | Driver can choose speed or detail without postponing the useful workflow. |
| TM-D028 | ACTIVE | Settlement reconciliation is line-by-line and load-based, not restricted to the week a load was completed. Completed loads can remain Awaiting Settlement and match when they appear on a later settlement; mismatches/accessorial pay are surfaced for review. | Carriers may move loads between settlement weeks. |
| TM-D029 | ACTIVE | Mileage preserves separate carrier-paid miles, TruckMate route-estimated miles, and driver-adjusted miles. Manual adjustment is allowed and clearly labeled while the original estimate remains in audit history. | Normal map routing is an estimate and may differ from truck-route/paid mileage. |
| TM-D030 | ACTIVE | User corrections to AI-extracted or system-estimated values preserve the original value and correction provenance/audit history while the corrected value becomes operationally active. | Trust, traceability, and legitimate correction. |
| TM-D031 | ACTIVE | User-deleted documents enter Trash for 30 days and can be restored during that window; after 30 days the file is permanently deleted. A linked record may retain only that a document was deleted, not the deleted file itself. TruckMate is not the carrier's official compliance-retention system. | User data control with accidental-deletion recovery. |
| TM-D032 | ACTIVE | Strong document signals may auto-advance load state: pickup papers/BOL can set In Transit; signed delivery BOL/POD can set Delivered. Users can manually override/correct state. | Reduce redundant taps while preserving recovery from unusual cases. |
| TM-D033 | ACTIVE | Rejected freight remains part of the same load story. Partial rejection is Delivered with Exception, recording rejected quantity/reason/photos/docs and freight still on truck. Full rejection keeps the load open/Awaiting Instructions. Return, alternate receiver, donation/food-bank, or other disposition is an additional stop on the same load, with additional compensation tracked separately as unknown, none, or amount. | Rejected freight is not a new load and may have later disposition/pay. |
| TM-D034 | ACTIVE | Facility intelligence uses proactive, opt-in post-stop driver reports rather than live nearby-driver requests/maps. Reports may cover parking, restroom, early unload and notes; show timestamp/source and surface recent TruckMate-driver information alongside conflicting public information. | Higher-value current facility knowledge without exposing driver location/history. |
| TM-D035 | SUPERSEDED | Monetization target is a 60-day full-feature trial followed by $59.98/month. Do not repeatedly change the public price without a deliberate later decision. | Full product experience first; target price is under $2/day. Superseded 2026-09-26: pricing by TM-D072, trial by TM-D073. |
| TM-D036 | SUPERSEDED | TruckMate remains only the working/project name. A different public name is required; naming decision remains intentionally open under TM-Q012. | Superseded by TM-D056 when the owner selected CabPilot and cabpilotapp.com. |
| TM-D037 | ACTIVE | TruckMate organizes records and evidence but shall not claim to guarantee DOT/legal/tax compliance, legal admissibility, detention payment, or court-proof evidence. | Product assistance must not be represented as a legal/compliance guarantee. |
| TM-D038 | ACTIVE | Export supports all data, any date range, one load, or selected loads. Financial export is an Excel workbook (summary, loads/income, expenses, settlements) bundled with original documents organized by load and referenced from the workbook. | Drivers/accountants need portable, understandable records for review and tax preparation. |
| TM-D039 | ACTIVE | Expenses are recorded in one expense system and are not required to be tied to a load. Truck/business expenses capture date, amount, category, location/address when useful, what was fixed/purchased, optional notes/line items, optional receipt/attachment, and vehicle/unit when useful. Common categories use quick-pick plus Other/custom; recurring costs such as insurance/subscriptions are supported. Reports show load-related/trip costs and truck/overhead costs separately plus combined totals/net. | Repairs/overhead happen both on-load and off-load; forcing a load link creates false bookkeeping. |

| TM-D040 | ACTIVE | V1 trailer types are **Dry Van** and **Reefer**. Trailer type controls which trailer-specific fields/checks appear. Architecture may allow Flatbed/Other/specialized types later without building their full workflows in V1. | Avoid irrelevant fields while keeping V1 focused and extensible. |
| TM-D041 | ACTIVE | V1 supports mid-load truck/trailer swaps and preserves equipment-assignment history. By default, a new assignment is effective from the swap forward; prior-stop/history metadata is not silently rewritten. | Drop-and-hook, breakdowns, relays, and equipment changes are normal real-world events. |
| TM-D042 | ACTIVE | Hooking/swapping a trailer triggers a **Quick Trailer Check** before confirming the new assignment. The driver may skip it with a reason; a more detailed trailer inspection may be used when needed. | Document condition at handoff without trapping the driver in a long workflow. |
| TM-D043 | ACTIVE | Reefer-specific V1 fields are limited to set-point temperature, operating mode, reefer fuel level, unit status/alarm, and optional actual temperature. | Capture high-value reefer information without turning TruckMate into a reefer-management system. |
| TM-D044 | ACTIVE | V1 includes a flexible **Critical Load Instructions** area for high-value special instructions such as seal number/do-not-break-seal, driver assist, pallet exchange, special handling, and similar load-specific directions. AI may extract these when present and the Current Load Card should surface them when relevant. | Avoid a growing list of niche fields while keeping critical instructions visible. |
| TM-D045 | ACTIVE | On a multi-stop load, the driver may select a different **Active Stop** without falsely completing earlier stops. Drag-and-drop reordering is not required as a primary V1 workflow; sequence editing may live in Edit Load if needed. | Real routes can be serviced out of listed order; the app must not force fake state changes. |
| TM-D046 | ACTIVE | Detention/free-time thresholds are configurable. V1 uses a 2-hour user default when no load-specific rule is known and may send a local reminder 15 minutes before the configured threshold. Messaging must not state or imply guaranteed billable detention. | Reuse check-in time to prevent missed detention follow-up while respecting carrier/load differences and claim boundaries. Clarified by TM-D058 (Onsite timer from arrival; neutral wording). |
| TM-D047 | ACTIVE | Offline/sync conflict handling follows provenance: a deliberate manual user correction outranks AI/inferred background data. Material manual-vs-manual conflicts must not be silently resolved solely by client/device timestamp; preserve competing versions/provenance and a recovery path. | Device clocks and concurrent edits can be wrong; important operational data should remain recoverable and auditable. |
| TM-D048 | ACTIVE | Operational progress, paperwork completeness, and settlement/reconciliation are separate parallel status dimensions rather than one forced linear state machine. | A delivered load can simultaneously have missing paperwork, appear on a settlement, or have an unresolved pay mismatch. |
| TM-D049 | ACTIVE | V1 does **not** add a separate Gate Pass screen. The Current Load Card must make gate/check-in references (pickup/release number, carrier, driver, truck, trailer, plate/state where available) quickly readable; a dedicated Gate View may be reconsidered only after field testing. | Preserve clean/easy/simple and avoid another screen unless real usage proves it is needed. |

| TM-D050 | ACTIVE | V1 adds one unified **Upcoming** due/reminder area for one-time expiration/due dates and recurring schedules; it is distinct from Upcoming/Pre-planned Loads. | Expirations, bills, maintenance and similar obligations share the same countdown/reminder pattern and should not become separate features. UI label is **Reminders** (TM-D057). |
| TM-D051 | ACTIVE | V1 login uses phone OTP with optional email and no password. Losing both phone and email does not create an automatic self-service recovery path in V1. | Keep login simple while avoiding insecure ad hoc recovery. Phone-number change defined by TM-D062. |
| TM-D052 | ACTIVE | V1 includes a lean admin/operations panel limited to Dashboard, Users, Subscriptions, Support/Recovery, and Controls. | Provide necessary operations capability without building a second product. |
| TM-D053 | ACTIVE | Admin roles are Owner, Admin, and Support. Administrative access does not grant access to private driver document contents; support may use limited metadata such as account/activity/upload time and city when available. | Preserve driver privacy while allowing practical support. |
| TM-D054 | ACTIVE | Working V1 tiers are Company Driver and O/O; O/O includes owner-operators and percentage-paid drivers needing financial/business features. Tier entitlements may be controlled without hard-coding job titles. | Keep access simple while matching functional needs. Naming applies everywhere; expenses available to both tiers (TM-D060). |
| TM-D055 | ACTIVE | After the Upcoming and lean admin additions, V1 feature scope is final/frozen. New feature ideas go to V2 unless a contradiction, security/privacy flaw, implementation blocker, or field-validated gap requires repair. | Stop scope creep and move from requirements into design/build. |
| TM-D056 | ACTIVE | Public product/store brand is **CabPilot**; approved primary domain is **cabpilotapp.com**. TruckMate may remain the internal repository/project working name. | Owner-selected 2026-09-23 (resolves TM-Q012). Row restored 2026-09-26: it was referenced across the repository but missing from this table. |

| TM-D057 | ACTIVE | UI naming (Claude design issue #1): the TM-D050 due/reminder module is labelled **Reminders**; future/pre-planned loads (TM-D018) are labelled **Next Loads**. "Upcoming" is not used as a UI label for either. Each reminder item shows its own due timing (e.g. "Truck payment · due in 3 days"). Naming change only; approved behaviour is unchanged; internal/document names may keep existing terms. | One word for two different things confused the Today screen in design review. |
| TM-D058 | ACTIVE | Stop timer (issue #4; clarifies TM-D046): the stop timer starts at actual arrival/check-in, always, regardless of appointment time. It is labelled **Onsite**, never "Detention", and the app never states or implies detention is owed. When a stop has an appointment time, show it beside the timer as "Appt [time]" (e.g. "Onsite 3h 10m · Appt 8:00 AM"). Threshold reminders use neutral wording (e.g. "Onsite 1h 45m"). Settlement reconciliation SHALL NOT automatically flag missing detention from the Onsite timer. Configurable threshold, 2-hour default, 15-minute reminder, and arrival provenance are unchanged. | Free time may count from arrival or appointment depending on the carrier; a neutral factual timer supports records without implying entitlement (TM-D037). |
| TM-D059 | ACTIVE | No in-motion restriction (issue #5; clarifies TM-D021): V1 has no in-motion restriction or driving mode of any kind — no lock, no automatic Driving view, no driving-mode button or toggle. Every feature, screen and action works fully at all times regardless of speed, motion or driver situation. TM-D021 remains a design principle only: core workflows should not require interaction while moving. Notifications and reminders may appear at any time, including while moving, but the app SHALL NEVER send a notification, pop-up or prompt that requires the driver to respond, type or act in order to dismiss or continue; any input-requiring step waits until the driver opens the app. Driving view (TM-F066) and fleet-admin in-motion lock (TM-F067) move to V2. | Motion detection cannot reliably distinguish passengers, team drivers or stopped traffic; V1 relies on design principle plus no-input notifications instead of enforcement. |
| TM-D060 | ACTIVE | Tiers and expenses (issue #2): tier names are **Company Driver** and **O/O** everywhere (TM-D054); "Standard/Pro" wording is retired. Expenses (TM-F029, TM-F054, SRS §29) are available to BOTH tiers. Other O/O financial-layer features stay O/O. Entitlements remain controllable per tier via admin Controls. | Consistent terminology; company drivers also need to record work expenses. |
| TM-D061 | ACTIVE | V1 candidates promoted (issue #12): TM-F016 (document type mismatch warning), TM-F019 (replacement-document recognition), TM-F022 (defect notes/photos/reminders) and TM-F027 (mileage-driver estimated weekly pay) are **V1 Core**. | A frozen baseline should not carry undecided candidates; all four were already designed in. |
| TM-D062 | ACTIVE | Phone number change (issue #13; fills gap in SRS §37 / TM-D051): a user can change their phone number in Settings. Required verification: OTP to the new number, plus confirmation through either the old number or the verified backup email. If neither is available, the case goes to the existing support/recovery process. | Planned number changes are common; a second confirmation channel prevents takeover via a new number. |
| TM-D063 | ACTIVE | Offline document scan (issue #3): an offline scan saves immediately; document-driven stage updates (TM-D032) apply when back online; manual "Mark In Transit" remains available. | Approved as assumed in the Claude Stage 1 design. |
| TM-D064 | ACTIVE | Check-out (issue #6): check-out is never implied silently. After POD, Check Out is highlighted but the driver taps it. | Approved as assumed; silent inference risks short/incorrect dwell records. |
| TM-D065 | ACTIVE | Facility report prompt (issue #7): the TM-D034 facility report prompt appears only inside the check-out flow while parked. | Approved as assumed; avoids prompting as the driver pulls away. |
| TM-D066 | ACTIVE | Reminder completion (issue #8): reminders can be marked done; recurring reminders advance to the next due date when marked done. | Approved as assumed; completes the TM-D050 item lifecycle without new scope. |
| TM-D067 | ACTIVE | Current load lifecycle (issue #9): a delivered load stays Current until the driver taps Start on the next load; Next Loads never auto-promote. | Approved as assumed; prevents paperwork on a just-delivered load from being attributed to the wrong load. |
| TM-D068 | ACTIVE | Notification classes (issue #10): Settings lists five notification classes (expirations, reminders, Onsite threshold reminder, open defects, facility report prompts), each switchable; all follow the TM-D059 no-input rule. | Approved as assumed; aligns SRS §17 with TM-D034/D046/D050. |
| TM-D069 | ACTIVE | Setup tier question (issue #11): setup asks "How are you paid?" (Company Driver / O/O); the trial unlocks all features for both tiers. | Approved as assumed; tier-adaptive UI without crippling the trial (TM-D014). |
